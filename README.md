# HBF — Host-Based Firewall

**HBF** — система централизованного управления сетевыми политиками Linux-серверов на базе `nftables`.

Проект объединяет веб-интерфейс администратора, центральный контроллер и агенты на управляемых узлах. HBF позволяет создавать правила фильтрации, проверять изменения перед применением, развёртывать конфигурации и контролировать состояние серверов из единой консоли.

**Текущая версия:** Alpha 1.4 R2  
**Статус:** Alpha / Development

---

## Возможности

- **Централизованное управление** — работа с несколькими Linux-серверами из одной Web Console.
- **Сетевые политики** — фильтрация TCP, UDP и ICMP с действиями `ACCEPT`, `DROP`, `REJECT`.
- **Гибкая настройка** — порты, диапазоны, CIDR, приоритеты, состояния соединений и логирование.
- **YAML / JSON** — импорт и экспорт конфигураций политик.
- **Безопасный Deploy** — предварительная проверка, последовательное применение и механизмы отката.
- **Quarantine** — ограничение сетевого взаимодействия отдельного узла с сохранением предусмотренного административного доступа.
- **Мониторинг и аудит** — статусы агентов, история изменений, журнал операций и визуализация топологии.

## Архитектура

```text
                    Administrator
                          |
                     Web Console
                          |
                    HBF Controller
                          |
                SSH / Agent Protocol
                          |
              +-----------+-----------+
              |           |           |
           Node 01     Node 02     Node N
              |           |           |
           HBF Agent   HBF Agent   HBF Agent
              |           |           |
           nftables    nftables    nftables
```

| Компонент | Назначение |
|---|---|
| **Controller** | Хранение политик, управление узлами и координация Deploy |
| **Web Console** | Графический интерфейс администратора |
| **Agent** | Применение правил nftables и контроль локального состояния |
| **Ansible** | Первоначальная установка и регистрация узлов |
| **SQLite** | Хранение конфигураций, истории и данных контроллера |

Взаимодействие контроллера с агентами осуществляется через SSH с ограниченными привилегиями.

## Установка

### 1. Требования

- Linux-сервер для контроллера и Linux-узлы с доступным SSH.
- Python 3 и необходимые системные пакеты.
- Ansible на управляющей машине.
- `nftables` и `systemd` на управляемых узлах.
- Права администратора (`sudo`/root).
- Сетевая доступность управляющих IP-адресов.

**Совместимость:** текущий установочный playbook рассчитан на Linux-дистрибутивы семейства Debian с пакетным менеджером APT, включая Debian, Ubuntu и Kali Linux. Для RHEL-подобных и других дистрибутивов требуется адаптация Ansible-ролей и проверка зависимостей.

### 2. Получение исходного кода

```bash
git clone https://github.com/2L1nks/hbf-alpha.git
cd hbf-alpha
```

Для приватного репозитория необходим авторизованный доступ GitHub.

### 3. Настройка узлов

Отредактируйте файл `bootstrap/inventory.yml`, указав управляющие адреса серверов и параметры SSH.

Пример:

```yaml
all:
  children:
    controller:
      hosts:
        controller01:
          ansible_connection: local
          hbf_host_ip: 10.0.0.10

    hbf_nodes:
      hosts:
        controller01:
          ansible_connection: local
          hbf_host_ip: 10.0.0.10

        server01:
          ansible_host: 10.0.0.11
          ansible_user: admin
          hbf_host_ip: 10.0.0.11
```

В этом примере Ansible запускается непосредственно на контроллере. Для удалённого контроллера настройте SSH-подключение к нему.

Группа `controller` определяет центральный сервер, а `hbf_nodes` — управляемые узлы, включая сам контроллер при необходимости.

### 4. Развёртывание

Установите Ansible средствами своего дистрибутива, затем выполните из каталога проекта:

```bash
cd bootstrap

ansible-inventory -i inventory.yml --list

ansible hbf_nodes -i inventory.yml -m ping -k

ansible-playbook -i inventory.yml install.yml -k -K
```

Параметры `-k` и `-K` запрашивают SSH-пароль и пароль повышения привилегий. При использовании SSH-ключей и настроенного `sudo` параметры можно скорректировать.

Ansible установит контроллер, зарегистрирует узлы, настроит агентов, необходимые права и службы восстановления.

### 5. Создание администратора

На сервере контроллера выполните:

```bash
sudo -u admin_hbf \
  /opt/hbf-alpha/venv/bin/python \
  /opt/hbf-alpha/controller/app.py init-admin
```

Задайте имя пользователя и надёжный пароль для входа в Web Console.

### 6. Запуск Web Console

После установки интерфейс доступен на контроллере:

```text
http://127.0.0.1:8088
```

Для удалённого доступа рекомендуется SSH-туннель:

```bash
ssh -N -L 8088:127.0.0.1:8088 admin@CONTROLLER_IP
```

Затем откройте `http://127.0.0.1:8088` на своём компьютере.

По умолчанию Web Console слушает только loopback-интерфейс. Не рекомендуется открывать её напрямую в недоверенной сети.

## Начало работы

После установки HBF используется следующая последовательность:

1. **Hosts** — добавьте в рабочую конфигурацию узлы, зарегистрированные через Ansible.
2. **Policies** — создайте правила фильтрации через Web Console или импортируйте YAML.
3. **Plan / Diff** — проверьте предполагаемые изменения.
4. **Preflight** — убедитесь в готовности агентов.
5. **Deploy** — подтвердите применение конфигурации.
6. **Audit / Status** — проверьте результат и состояние узлов.

Создание или импорт политики **не применяет её автоматически**. Изменения вступают в силу только после отдельного Deploy.

### Пример YAML-политики

```yaml
version: 1

policies:
  - id: APP-DB-001
    name: ALLOW-APP-DB
    description: "Application access to database"
    enabled: false

    source: app01
    destination: db01

    family: ipv4
    protocol: tcp
    destination_port: 5432

    action: accept
    priority: 10
```

`source` и `destination` должны ссылаться на существующие узлы HBF.

Для импорта используйте **Система → Импорт YAML**.

Поддерживаются два режима:

| Режим | Поведение |
|---|---|
| `merge` | Добавляет новые и обновляет существующие политики по ID |
| `replace` | Заменяет весь набор политик содержимым файла |

Перед подтверждением HBF показывает предпросмотр изменений. Рекомендуется использовать `merge`, а перед `replace` сохранять резервную копию конфигурации.

YAML в Alpha 1.4 используется для **политик**, но не для автоматической установки или регистрации новых серверов.

## Управление состоянием

HBF использует транзакционный механизм Deploy:

`STAGE → ARM → APPLY → VERIFY → COMMIT`

При ошибках предусмотрены операции отката.

Основные статусы:

| Статус | Описание |
|---|---|
| `CLEAN` | Агент находится в согласованном состоянии, незавершённых операций нет |
| `STAGED` | Новая конфигурация подготовлена |
| `ARMED` | Подготовлено безопасное применение изменений |
| `APPLIED` | Изменения применены |
| `SUCCESS` | Deploy успешно завершён |
| `FAILED` | Deploy завершился с ошибкой |
| `PARTIAL` | Конфигурация могла примениться не на всех узлах |

Статус `PARTIAL` требует ручной проверки согласованности агентов. Само подтверждение статуса не исправляет расхождения.

## Диагностика

На сервере контроллера:

```bash
systemctl status hbf-alpha-console.service

curl -I http://127.0.0.1:8088/
```

На управляемом узле:

```bash
sudo /usr/local/sbin/hbf-alpha-agent status

sudo nft list table inet hbf_alpha

systemctl status hbf-alpha-restore.service
```

Текущие применённые правила необходимо сверять с ожидаемой конфигурацией. Статус `CLEAN` не означает отсутствие firewall-правил.

## Безопасность и ограничения

HBF Alpha 1.4 R2 находится в стадии разработки. Перед использованием в производственной инфраструктуре необходимы аудит безопасности и дополнительные испытания.

Следует учитывать:

- Сохранение доступа к управляющим портам TCP/22 и TCP/8088.
- Зависимость Deploy от доступности и согласованности агентов.
- Необходимость контроля операций `PARTIAL` и восстановления.
- Отсутствие автоматического создания серверов и VLAN.
- Незавершённое тестирование IPv6 и масштабных развёртываний.
- То, что HBF не заменяет сетевую сегментацию и межсетевые экраны периметра.

Не публикуйте закрытые ключи, пароли, рабочие Inventory и базы контроллера в репозитории.

Подробные рекомендации приведены в [`SECURITY.md`](SECURITY.md).
